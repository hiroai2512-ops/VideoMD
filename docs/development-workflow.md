# アプリ開発フロー

対象工程の節を参照する。
常時適用する指示はルートの [AGENTS.md](../AGENTS.md)、Plus 向けの工程運用は [efficient-development.md](efficient-development.md) にあります。
チェックは変更の影響に応じて選び、適用対象外は理由を記録します。文書のみの変更にアプリのビルドを要求しません。

## 1. 目標

- ユーザーが本当に必要としている課題を、小さく安全に解決する。
- 読みやすく、テストでき、保守しやすいコードを作る。
- 設計から本番公開後の運用までを一つの開発プロセスとして扱う。
- セキュリティ、プライバシー、アクセシビリティ、性能、運用性を後付けにしない。
- 判断の理由と未解決事項を、コードまたは文書に残す。

## 2. 開発を始める前に確認する情報

実装前に、少なくとも次の情報を明確にする。分からない項目は仮定を明記し、影響が大きい場合はユーザーに確認する。

### プロダクト

- 誰が使うのか（対象ユーザー）
- どんな課題を解決するのか
- 最も重要な利用シナリオは何か
- MVP に必要な機能と、今回は作らない機能
- 成功を判断する指標（利用数、完了率、継続率、応答時間など）
- 対応する言語、地域、端末、ブラウザ

### 技術・運用

- Web、モバイル、デスクトップ、API などの提供形態
- 使用する言語、フレームワーク、データベース、外部サービス
- 認証・認可の要否とユーザー権限
- 保存するデータ、その機密度、保存期間、削除方法
- 想定トラフィック、性能目標、可用性目標
- 開発・ステージング・本番の各環境
- 公開先、ドメイン、予算、納期、運用担当者
- 法令、利用規約、ライセンス、プライバシー上の制約

### 新規アプリの開始準備

新しいアプリを作るときは、まずユーザーがローカルにアプリ専用フォルダを作り、Codex Core の必要な内容を手動でコピーして、そのフォルダで Codex を始める。具体的なコピー対象と順序は [README.md](../README.md) に記す。Codex Core は開発ルールのリポジトリとして扱い、アプリのソースコードはユーザーが用意したアプリ専用フォルダと、その後接続する専用リポジトリに保存する。既存アプリの継続作業では、専用フォルダ・リポジトリ・Codex プロジェクトの対応を確認する。

1. Codex は作業フォルダがユーザーの用意したアプリ専用フォルダであることと、コピーされた `AGENTS.md` 等を確認する。ユーザーの既存ファイルや Git 履歴があれば保持する。
2. ユーザーの構想を壁打ちし、アプリの目的、対象ユーザー、主な機能、名前の候補を整理する。詳細な設計をすべて確定する必要はない。GitHub の作成先アカウントまたは組織、リポジトリ名、公開範囲（private/public）も決める。重要な未決定事項はユーザーに確認する。
3. Codex デスクトップアプリで、そのアプリ専用のローカルプロジェクトを作成し、**手順1の同じフォルダ**を主フォルダに設定する。既に専用プロジェクトがある場合は、その設定を確認する。プロジェクトのフォルダ設定は [OpenAI Docs の Projects and chats](https://learn.chatgpt.com/docs/projects) を参照する（2026-10-01 確認）。
4. アプリ専用の GitHub リポジトリを作る。GitHub の[新規リポジトリ作成ページ](https://github.com/new)を使うか、CLI で `gh repo create OWNER/REPO --private`（公開する場合のみ `--public`）を使う。**`--clone` で別の作業フォルダを作らない。** 別のアプリや Codex Core と共用しない。画面の操作は [GitHub 公式手順](https://docs.github.com/en/get-started/start-your-journey/creating-a-repository-for-your-project-on-github)、CLI のオプションは [GitHub CLI 公式手順](https://cli.github.com/manual/gh_repo_create) を参照する（2026-10-01 確認）。
5. 手順1のフォルダで Git を初期化し、作成したリポジトリを `origin` に接続する。既に Git 履歴や `origin` がある場合は、[初回保存](#着手と初回保存)の規則に従い、既存のファイルと履歴を保持して整合させる。GitHub から clone してユーザーのフォルダを置き換えない。
6. 作業フォルダ、Codex プロジェクトの主フォルダ、Git ルートが同じアプリのフォルダで、`origin` が専用リポジトリを指すことを確認する。`git rev-parse --show-toplevel`、`git remote get-url origin`、GitHub のリポジトリページで照合する。リポジトリ名・公開範囲・Codex プロジェクト名・主フォルダを `docs/Plan.md` の開始記録に残す。秘密情報を含む URL は記録しない。

この対応が確認できるまでアプリ本体の実装に進まない。構想整理や要件の記録は進めてよい。リポジトリ作成や Codex プロジェクト設定を実行できない場合は、未完了の項目と理由を記録する。リポジトリの作成・初回プッシュ時は、[Git と変更管理](#5-git-と変更管理) の公開範囲、送信対象、CI/CD の確認規則にも従う。

## 3. 標準開発フロー

### Phase 1: 課題定義とスコープ決定

新規アプリや重要な未決事項がある変更は、[独自プランモード](work-modes.md) で現状調査とステップバック・クエスチョンを行い、ユーザーの目的から要件・設計・実装計画へ落とし込む。内蔵プランモードは使わない。要件が明確な小修正では通常モードで進める。

1. ユーザーの課題を一文で定義する。
2. 主要な利用者とユースケースを整理する。
3. 機能を「必須」「後で追加」「対象外」に分類する。
4. 受け入れ条件を、確認可能な文章で定義する。
5. リスク、前提、未決定事項を記録する。

成果物: `docs/requirements.md`。目的、利用シナリオ、機能一覧、対象外、ID付きの受け入れ条件を記載する。

### Phase 2: UX・UI 設計

1. ユーザーが目的を達成するまでの画面遷移を決める。
2. 主要画面のワイヤーフレームを作る。
3. 正常時だけでなく、空状態、読込中、エラー、権限不足も設計する。
4. キーボード操作、色のコントラスト、ラベル、フォーカス順などのアクセシビリティを確認する。
5. モバイルとデスクトップの表示方針を決める。

見た目より先に、迷わず操作できる情報構造と導線を優先する。
画面と状態の仕様は `docs/design/ui.md` に記録する。画面のないアプリは作成不要。

### Phase 3: 技術設計

実装前に、必要な範囲で次を決める。

- システム構成と責務の境界
- データモデル、制約、インデックス、マイグレーション方針
- API の入出力、エラー形式、認証・認可
- 外部サービスとの連携方法、タイムアウト、再試行、障害時の挙動
- キャッシュ、非同期処理、ファイル保存の方針
- ログ、メトリクス、トレース、アラートの方針
- バックアップ、復元、ロールバックの方法

構成と主要な判断は `docs/architecture.md`、必要な API・データ詳細は `docs/design/api.md` と `docs/design/data.md` に記録する。重要な選定の候補、採用理由、欠点も含める。新しい依存関係は、必要性、保守状況、ライセンス、サイズ、セキュリティを確認してから追加する。

#### 外部サービスの料金と無料案

外部API・サーバー・ホスティング・DB・認証・ストレージ等を提案または採用するときは、採用前に以下をユーザーへ説明し、構成の選定理由と一緒に保存する。追加・プラン変更・利用量増加で費用条件が変わるときも更新する。

- 案内時点の公式料金ページと確認日、プラン、通貨、課金単位。初期費用、月額固定費、従量費、最低料金、税の扱いを区別する。
- 利用者数、月間API回数、処理量、保存量、通信量等の見積前提と計算式。小規模利用と想定利用量の月額目安を示す。不明な前提は質問または仮定を明記する。
- 無料枠の上限・期限・商用利用等の条件、カード登録の要否、上限超過時の課金または停止、予算通知・利用制限の可否。試用期間を恒久無料と説明しない。
- 外部サービスを使わない無料案（ローカル実行、端末内保存、静的構成、手作業等）を少なくとも1案。サービスの無料枠案とは区別する。既存PCを使う前提や電気代、運用時間、公開・同期・複数利用者・精度・処理速度の制約も示す。同じ機能を無料で実現できなければ、その差を明記する。

比較は次の項目で簡潔な表にする。

| 案 | 初期・月額費用と前提 | 無料枠・超過条件 | できること・制約 | 開発速度・運用負担 |
| --- | --- | --- | --- | --- |
| 外部サービスを使う案 | 公式単価×想定量＋固定費 | 上限・課金/停止 | 機能・品質・可用性 | 導入と保守の手間 |
| 外部サービスを使わない無料案 | 追加サービス料金0、既存端末等の前提 | 該当なし | 公開・同期等の差 | 実装と手作業の手間 |

料金や無料条件を確認できなければ「未確認」とし、数字を作らない。為替換算はレートと確認日を添えた概算にする。見積を確定請求額と説明しない。推奨案と採用理由を示し、課金・契約・権限付与は依頼の承認範囲に従って実行する。

### Phase 4: 実装計画

- 作業を、小さく独立して検証できる単位に分割する。
- 依存関係の強い順ではなく、価値とリスクを早く検証できる順に進める。
- データ破壊、認証、決済、個人情報、外部公開に関わる変更は特に小さく分ける。
- 各タスクに受け入れ条件とテスト方法を持たせる。

推奨順序は、最小の縦切り機能（画面からデータ保存まで）を完成させ、その後に機能を広げること。土台だけを長期間作り続けない。
計画は `docs/Plan.md` に Step 見出しとID付きチェックボックスで記録する。完了・検証・中断・スコープ変更の節目に更新する。書式と進行条件は [文書管理](documentation.md) に従う。

独自プランモードの最終成果物にもこの実装計画書を含める。必須の利用導線を満たす完成度6割程度のMVPを先に計画し、任意の仕上げは対象外として分ける。複数ターンの反復が必要なら内蔵ゴールモードを候補にするが、起動は [モード運用](work-modes.md) の条件に従う。

### Phase 5: 実装

- 既存コード、設定、命名、ディレクトリ構成を確認してから変更する。
- 要求を満たす最小限の変更を行い、不要な全面改修を避ける。
- 複雑な処理は小さな関数・モジュールに分け、責務を明確にする。
- 入力値は信頼せず、境界で検証する。
- エラーを握りつぶさず、ユーザー向け表示と運用ログを分ける。
- 時刻、通貨、文字コード、ロケール、タイムゾーンを明示的に扱う。
- 公開 API や重要な処理には、意図と制約が分かる文書を付ける。
- コメントは「何をしているか」ではなく「なぜそうするか」を説明する。
- 一時的な回避策には理由、影響、解消条件を残す。

### Phase 6: テストと品質確認

変更に応じて、次のテストを組み合わせる。

- 単体テスト: 計算、分岐、変換、バリデーション
- 統合テスト: API、データベース、外部サービスとの境界
- E2E テスト: 最重要のユーザーフロー
- 手動確認: 表示、操作感、レスポンシブ、アクセシビリティ
- 非機能テスト: 性能、負荷、障害復旧、セキュリティ

最低限、正常系、入力不正、権限不足、データなし、外部障害を確認する。バグ修正では、可能な限り先に再現テストを追加する。

変更完了前に、以下から影響範囲に必要なチェックを実行する。

- フォーマット
- Lint・静的解析
- 型チェック
- 自動テスト
- ビルド
- 依存関係と脆弱性の確認

実行できなかった項目は、理由と残るリスクを報告する。

### Phase 7: レビューとリリース準備

- 指摘の分類と追加修正は、次の「レビュー後の修正ループ」に従う。
- 差分が要件と一致しているか確認する。
- 意図しないファイル、デバッグコード、ログ、秘密情報が含まれていないか確認する。
- データベース変更の後方互換性とロールバック手順を確認する。
- 環境変数、インフラ設定、権限、ドメイン、証明書を確認する。
- リリースノートと、必要ならユーザー向け案内を用意する。
- ステージング環境で本番相当の確認を行う。

#### レビュー後の修正ループ

以下はこのリポジトリの優先度基準。重要度は変更行数や修正の容易さではなく、具体的な発生条件と利用者への影響で決める。

| 優先度 | 基準と例 | レビュー後の対応 |
| --- | --- | --- |
| P0: 緊急 | 現在発生中またはリリース直後に不可避の、広範な停止・重大な情報漏えい・不可逆なデータ損失 | 影響する公開・作業を止め、修正を最優先。復旧操作は承認範囲内で行う |
| P1: 高 | 具体的な条件で主要導線が使えない、有効な回避策がない重大な不具合、認可漏れ・誤課金・データ破損など | 次の関連工程・公開前に修正と検証を行う |
| P2: 中 | 影響が限定的、回避策のある非主要機能の不具合など、P0/P1に該当しない問題 | 記録のみ。追加実装しない |
| P3: 低 | 見た目、命名、任意の整理、実害のない改善提案 | 記録のみ。追加実装しない |

1. reviewer（またはメインの自己レビュー）が、指摘ID・優先度・ファイル位置・発生条件・影響・根拠を返す。未検証の推測は候補と明示する。
2. メインが根拠を確認して優先度を確定する。重大な疑いで安全に再現できない場合はコード経路等の証拠で判断し、必要な確認まで公開を保留する。
3. 確認された P0/P1 だけを `docs/Plan.md` の該当 Step に修正タスクとして加え、最小の修正と関連テストを行う。P2/P3 を同時に便乗修正しない。
4. 修正箇所とその影響範囲だけを再レビューする。修正で生じた P0/P1 も同じ扱いとする。
5. 未解決 P0/P1 がなく、必要な検証を終えたらループ終了。P2/P3 が残っていても、その修正のためにはループを続けない。

P2/P3 は `docs/reviews/<task-id>.md` に短く残すだけとし、Plan の未完了修正タスクにしない。後でユーザーが明示的に修正を依頼した場合に別タスクとして扱う。指摘がない場合は Plan の検証欄に一行で済ませる。
新証拠のない同じ修正が2回続いたら、再現条件と試行をまとめて手法を見直す。未解決を残して完了扱いにせず、必要なら役割の昇格条件で判断する。

この制限はレビューが提案する追加修正に適用する。合意済み要件の通常実装を省略する理由にはしない。一方、P2/P3の指摘を修正したいだけで P1 に格上げしない。受け入れ条件の未達が判明しても、軽微なレビュー指摘を自動修正する抜け道にせず、未達を報告して要件の扱いを確認する。未達を残したまま全要件完了とは報告しない。

### Phase 8: 本番デプロイ

1. 本番データのバックアップと復元可能性を確認する。
2. デプロイ前の品質ゲートがすべて成功していることを確認する。
3. 段階リリース、Feature Flag、Blue-Green など、影響を限定できる方法を優先する。
4. マイグレーションはアプリとの互換性を維持できる順序で適用する。
5. デプロイ直後にヘルスチェックと主要ユーザーフローを確認する。
6. エラー率、応答時間、リソース使用量、主要指標を監視する。
7. 問題が許容範囲を超えた場合は、事前に決めた手順でロールバックする。

本番への公開、課金の発生、データ削除、外部への通知など、重大または取り消しにくい操作は、対象と影響を明示して承認を得てから実行する。

### Phase 9: 公開後の運用

- エラー監視、性能監視、稼働確認、アラートを設定する。
- バックアップを定期実行し、復元テストも行う。
- 依存関係とランタイムを定期的に更新する。
- インシデント時は、検知、影響抑制、復旧、原因分析、再発防止の順で対応する。
- ユーザーフィードバックとプロダクト指標から次の改善を決める。
- 不要になったデータ、権限、Feature Flag、インフラを安全に整理する。

## 4. セキュリティとプライバシー

- API キー、パスワード、トークン、秘密鍵をコードや Git に保存しない。
- 秘密情報は環境変数または Secret Manager で管理し、`.env.example` には名前と説明だけを書く。
- 認証だけでなく、すべての保護対象操作で認可を確認する。
- 最小権限を原則とし、管理者権限を常用しない。
- SQL、HTML、シェル、ファイルパスなどへの入力を適切に検証・エスケープする。
- 個人情報やトークンをログに出力しない。
- 保存時と通信時に必要な暗号化を行う。
- CSRF、XSS、SQL インジェクション、SSRF、パストラバーサル、レート制限を設計時に検討する。
- アップロードファイルは種類、サイズ、保存先、公開範囲を制限する。
- ユーザーデータの取得、利用、保持、エクスポート、削除方針を明確にする。
- 脆弱性を見つけた場合は、詳細を不用意に公開せず、影響範囲を確認して優先的に修正する。

## 5. Git と変更管理

### 保存の段階とタイミング

| 操作 | 目的 | 行うタイミング |
| --- | --- | --- |
| ファイルのローカル保存 | 現在の内容をPC上へ反映する | 編集の都度。Step完了まで待たない |
| 作業ブランチの作成 | 変更履歴をmainから分ける | 独立した機能・修正・文書整備に着手する前。関連する作業ブランチがあれば再利用 |
| ローカルコミット | 後から比較・復元できる履歴を残す | 一つの意味ある作業と必要な検証が完了した直後。関連するPlan更新も含める |
| 作業ブランチのプッシュ | コミットをGitHubにも保存する | 許可された範囲で、Step完了時、作業終了時、引き継ぎ前。未送信コミットがある場合だけ |
| PR・mainへのマージ | 確認済みの変更を共有の基準へ統合する | 対象の機能・修正が完成し、必要な検証とP0/P1修正が終了した後。PR作成・マージの依頼範囲に従う |

ブランチを作るだけでは未コミットの編集は履歴にならない。コミットはそのPC内の履歴であり、プッシュ前はGitHubに保存されていない。プッシュも本番公開とは別だが、連携されたCI/CDを起動する場合がある。

### 着手と初回保存

- メインがGit操作を担当する。子は変更と検証結果を返し、共有作業領域で勝手にブランチ切替・コミット・プッシュをしない。
- 着手時に現在のブランチ、変更済み・未追跡・ステージ済みファイル、リモート、追跡先を確認する。既存のユーザー変更を混ぜたり消したりしない。
- 通常の開発依頼では作業ブランチとローカルコミットを標準とする。保存方法が明示されていればそれに従う。説明・調査だけの依頼や、このルールの編集だけを理由に既存ファイル一式をコミット・プッシュしない。
- ブランチ名は `feat/<task-id>-<内容>`、`fix/<task-id>-<内容>`、`docs/<内容>` を基本に、半角英小文字とハイフンで付ける。共有のmainへ直接実装しない。関係のない作業へ移るときだけ分ける。
- 初回コミットがまだない場合は、リモートに既存履歴があるか確認する。ある場合はその履歴を基準に、ローカルファイルを保持して整合させる。確認できなければ独立した履歴を勝手に送信しない。
- リモートも空なら、保存対象を確定して最初の履歴を作る。既存の未追跡ファイル一式は依頼対象か確認し、秘密情報・生成物等を除外する。初回の土台だけはmainへのコミット可とし、その後の変更は作業ブランチで行う。

### コミットの単位と中断時

- 原則はPlanのタスク単位。ただし、単独では意味が通らない細かなタスクはまとめ、大きなタスクは独立して検証できる単位に分ける。Step全体の完成まで履歴を残さず待たない。
- コード・関連テスト・仕様変更・Planのチェック更新を一組にする。要件や設計など文書だけの成果も、内容と参照を検証した節目でコミットする。
- コミット前に差分とステージ対象を確認する。対象ファイルを指定して追加し、他者の変更、秘密値、不要なビルド成果物を巻き込まない。既存のステージ内容が混在していれば、勝手に解除・コミットせず切り分ける。
- メッセージは `feat: S3-02 入力内容の保存を追加` のように目的を示す。P0/P1修正には指摘IDを関連付ける。P2/P3をコミットのついでに修正しない。
- 中断・環境切替・大きな構造変更の前は、失いたくない進捗を保存する。検証可能な単位は通常コミットにし、途中状態しか残せない場合は作業ブランチに `wip: <task-id> <残作業>` のチェックポイントを作れる。
- WIPではPlanのチェックを付けず、未検証・失敗中の状態と再開手順を記録する。mainへマージせず、完成と報告しない。Git操作ができなくてもローカルファイルを保持して状況を伝える。

### プッシュ・マージの範囲

- プッシュ前に対象リポジトリ・送信ブランチ・未送信コミット・公開範囲・CI/CDの発火条件を確認する。新たな本番公開や課金等を伴う場合は、その操作まで既存の承認に含まれるか確認する。
- リモートURLが設定されているだけではプッシュ許可とは扱わない。ユーザーが特定のリポジトリ・作業ブランチへの継続的なプッシュを許可した場合は、以後同じ範囲の各節目で再確認せず行う。未承認なら送信準備まで整え、未プッシュであることを伝える。
- 作業終了時や引き継ぎ前は、完成したコミットと、バックアップが必要なWIPコミットを許可済みの作業ブランチへ送る。WIPを送る場合も未完成と明示する。短時間の状態確認やファイル保存ごとにプッシュしない。
- プッシュ失敗は成功として扱わない。原因を確認し、ローカルコミットを保持する。認証情報不足なら必要な設定を案内し、履歴の競合をforce pushで解消しない。
- mainへのマージは必要な検証の成功と未解決P0/P1がないことを確認する。P2/P3の修正はマージ条件にしない。CI失敗を無視せず、例外が必要なら理由と承認を記録する。
- PRには目的、主要変更、検証結果、既知の制約、必要なら画面画像とロールバック方法を記載する。プッシュの許可とマージ・本番公開の許可を混同しない。
- 履歴を書き換える操作、force push、ブランチ削除などは通常の保存処理に含めない。明示された必要性と権限がない限り行わない。

### 保存結果の報告

完了・中断時には、ローカル保存の有無、ブランチ、作成したコミットID、プッシュ先と成否を短く伝える。行わなかった操作は理由を示す。コミットやプッシュの成功はコマンド結果を確認し、必要に応じてローカル先端とリモート先端の一致を確認する。機密を含む接続URLは表示しない。

## 6. ドキュメント

保存先・内容・作成時期・更新の基準は [文書管理](documentation.md) を正本とする。コードと挙動を変更したら関連する文書も同じ変更内で更新する。小さな変更に不要な文書を新設しない。

## 7. 完了の定義（Definition of Done）

機能または変更は、次を満たしたときに完了とする。

- 受け入れ条件を満たしている。
- 主要な正常系と異常系がテストされている。
- 変更に適用されるフォーマット、Lint、型チェック、テスト、ビルドが成功している。対象外は理由が明確である。
- セキュリティ、プライバシー、アクセシビリティへの影響を確認している。
- 必要なログ、監視、エラー処理がある。
- 関連文書と設定例が更新されている。
- デプロイ方法とロールバック方法が明確である。
- 差分への秘密情報の混入を確認している。不要コード等のレビュー指摘は優先度基準で扱い、P2/P3の整理を完了の必須条件にしない。
- 残る制約や既知の問題が記録されている。
- 未解決の P0/P1 がなく、P2/P3 は修正せず必要な記録を残している。

## 8. 判断の優先順位

判断に迷った場合は、次の順で優先する。

1. ユーザーとデータの安全
2. 要件と正しい動作
3. 外部サービスの料金・規約・権限・障害対応の確認
4. 開発速度（完成度6割程度のMVPを早く届ける）
5. シンプルさ、必要な保守性・検証可能性・運用性
6. 必須条件を超える性能や見た目の仕上げ

この順位はプラン・ゴール・通常実装に共通する。6割は任意の仕上げを後回しにする目安であり、受け入れ条件、必要な検証、アクセシビリティやセキュリティを削る割合ではない。秘密情報の漏えい、データ損失、権限不備、意図しない課金、復旧不能につながる近道は選ばない。完了の定義は今回のMVPと影響範囲に必要な項目へ適用する。
