# 開発文書の保存・更新ルール

## 保存先と内容

ファイル名の大文字・小文字を表のとおり固定する。`docs/Plan.md` と `docs/plan.md` を併存させない。必要な工程に入ったときにフォルダとファイルを作り、空の仕様書一式を先に増やさない。

| 保存先 | 記載内容 | 作成・更新のタイミング |
| --- | --- | --- |
| `README.md` | アプリ概要、必要環境、セットアップ、起動、テスト、ビルドの実在するコマンド | 実行環境を作るとき。手順が変わる変更と同時に更新 |
| `docs/requirements.md` | 対象ユーザー、課題、利用シナリオ、必須機能、対象外、制約、`REQ-001`形式の受け入れ条件、未決事項 | 要件定義時。合意した要件の追加・変更時に更新 |
| `docs/architecture.md` | 技術構成、責務、依存関係、データフロー、非機能要件、主要な選択肢と採用理由 | 設計時。構成や契約の変更前に更新 |
| `docs/design/ui.md` | 画面遷移、画面ごとの入力・表示、空/読込/失敗/成功状態、操作とアクセシビリティ | 画面設計時。UI仕様変更時に更新。画面がなければ不要 |
| `docs/design/api.md` | エンドポイント、入力・出力、認証・認可、エラー、外部連携の契約 | API設計時。契約変更前に更新。APIがなければ不要 |
| `docs/design/data.md` | データ構造、制約、保存・削除、移行と復元方法 | 永続データ設計時。スキーマ・保持方針の変更前に更新 |
| `docs/Plan.md` | 最初は最小限の雛形。対話と要件・設計を踏まえたアプリ固有のStep、ID付き作業チェックリスト、依存関係、完了条件、検証証拠、ブロック、次の一手 | 新しいアプリへコピーし、作業開始前に具体化。完了・ブロック・仕様変更・引き継ぎ時に更新 |
| `docs/tasks/<task-id>.md` | Planの作業に対応する詳細な引き継ぎ。例: `docs/tasks/S3-02.md` | 会話をまたぐ調査・委譲など、Planの短い記録では不足するときだけ作成 |
| `docs/reviews/<task-id>.md` | 指摘ID、P0〜P3、位置、発生条件、影響、根拠、P0/P1の対応状態、P2/P3の記録 | レビューで指摘が出たときだけ作成。修正・検証後に更新 |
| `docs/deployment.md` | 環境、変数名、公開手順、DB移行順序、ヘルスチェック、ロールバック条件と方法 | ステージング構築前に作成。本番公開前に現状と照合 |
| `docs/operations.md` | 監視、障害対応、担当、バックアップ・復元、定期保守 | 本番公開前に作成。運用手順変更時に更新 |
| `.env.example` | 必要な環境変数の名前・説明・非秘密の例。秘密値は禁止 | 環境変数の追加・変更と同時に更新 |
| `docs/plans/completed/<plan-id>.md` | 完了したリリースまたは開発計画の最終スナップショット | 現在の計画が完了し、次の計画へ切り替えるときだけ保存 |

API定義やスキーマに機械可読の正本がある場合は、それを仕様書から参照し、同じ詳細を二重管理しない。仕様書は現在の仕様、Planは進捗、task-briefは再開情報を担当する。会話の経緯や挨拶、ツール試行の全履歴を記録しない。

## Plan.md の書式

- 独自プランモードの最終成果物としても `docs/Plan.md` を保存し、ユーザーにリンクを示す。ステップバック・クエスチョンで得た目的を要件IDに結び付け、実装Stepと検証へ対応させる。発動・実装へ進む条件は [モード運用](work-modes.md) を参照する。
- 今回のMVP、後回しの仕上げ、外部サービスの料金・無料案の比較への参照、重要な仮定と判断待ちを必要な範囲で記録する。計画策定中は未実装タスクにチェックを付けない。
- Codex Core 内の Plan は空に近い雛形とし、特定アプリの汎用 Step を完了済み・予定済みとして先に埋めない。コピー先でユーザーの構想を明確にし、要件・設計に対応する実行可能な計画へ書き換える。
- 現在のアクティブな計画は1つ。メインがチェック状態を統合し、子は担当タスクIDと結果を返す。子が並列にPlanを書き換えない。
- 冒頭に計画ID（例: `mvp-001`）、対象範囲、全体状態、現在のStep、次の一手を置く。
- `## Step 1: 要件定義` のような見出しの下に、`- [ ] S1-01: ...` 形式で独立して検証できる仕事を書く。
- 各Stepに依存条件と完了条件を置く。実装タスクは対応する要件IDと検証方法を指定する。
- タスクIDを付け替えたり再利用したりしない。チェック済みのものを修正する必要が出たら再オープン理由を一行残す。
- 作業が終わっても未検証なら `[ ]` のまま「検証待ち」とする。必要な検証の成功、または検証対象外の理由を確認してから `[x]` にする。
- 取り消したタスクはチェック済みにせず、現在のチェックリストから外して「対象外: ID・理由」に一行記録する。失敗やブロックを対象外にして隠さない。
- Stepの有効なタスクをすべて完了し、完了条件を満たしてから次のStepへ進む。同一Step内の独立した作業は並行可能。

## 更新する節目

1. 着手前: 目的、対象、依存関係、検証方法を確定し、現在のStepを設定する。
2. タスクの実装と検証が揃った直後: チェックを付け、コマンドと結果または証拠への参照を一行で記録する。
3. ブロック・前提変更・P0/P1の追加が発生した時点: 次の依存作業へ進む前に、未完了事項と次の一手を更新する。
4. Step完了時: 全タスクと完了条件を確認し、現在のStepを次へ進める。
5. 作業中断、ユーザーへの完了報告、別会話への引き継ぎ前: 実際の状態とPlanを一致させる。毎回の読込やツール実行ごとの更新は不要。

Planの更新はファイル保存であり、GitへのコミットやGitHubへのプッシュを意味しない。完了した作業のコード・テスト・Plan更新は同じコミットにまとめ、Step完了・作業終了・引き継ぎ時のプッシュは [Git と変更管理](development-workflow.md#5-git-と変更管理) に従う。コミットIDを同じコミット内のPlanに埋め込もうとして履歴を書き換えず、完了報告または後続の引き継ぎで示す。

レビュー後はP0/P1だけをタスク化する。P2/P3はレビュー記録へのリンクを置くにとどめ、次のStepの進行をその修正のために止めない。ただし、別途必要な受け入れ条件や検証が未達なら完了扱いにはしない。

完了した計画は、次の計画開始時に `docs/plans/completed/<plan-id>.md` へ保存してから、新しいIDのPlanに切り替える。未完了計画を完了フォルダへ移さない。過去計画は毎回読み込まない。

## 小さな変更の扱い

独立した小変更は現在のPlanに必要なタスクだけ追加する。計画全体が不要な一回限りの文言修正などは、短い作業説明と検証結果で足り、新たな要件書・設計書・引き継ぎファイルを作らない。アプリの新規開発や複数工程にまたがる機能はPlanで追跡する。
