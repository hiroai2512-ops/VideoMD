# Plus 向けの効率的な開発運用

出典と矛盾の解決は [調査記録](research/plus-agent-strategy.md)、設定方法は [.codex/README.md](../.codex/README.md)。

この文書の Sol は GPT-6.1 Sol（`gpt-6.1-sol`）を指す。メイン・implementerはmedium、reviewerはhighを運用の起点とする。Luna・Astraの役割は維持し、モデル変更による使用量・速度の改善率は実測する。

## 何を最適化するか

評価対象は「受け入れ条件を満たした変更1件あたりの使用量・時間・手戻り」。回答の短さや最小モデルの利用率だけを目標にしない。
Plus の利用枠は入力トークンだけで決まらず、モデル、推論、ツール、コンテキストなどに依存する。子に分けた仕事も消費する。API の料金比率を Plus の残量比率に換算しない。
Pro も無制限と仮定しない。長時間の多重実行や追加課金を前提にしない構成で進める。

## メインとサブの責務

メイン Sol が仕様・依存関係・受け入れ条件・統合結果の責任を持つ。自分で完結できる小変更は自分で実装する。
役割の一覧は [.codex/README.md](../.codex/README.md) が入口。子は常駐チームではなく、必要な仕事が発生したときだけ起動する。

次の条件をすべて満たすときに委譲する。

1. 目的・範囲・返却物が具体的で、親の次の判断待ちにならずに進められる。
2. 親にも並行して進められる有用な作業がある。
3. 重複調査や統合の手間を含めても、時間短縮・品質向上・親の履歴整理の利益がある。

標準は子0〜1、最大2。2つにする例は、メインが統合計画を作り、scout が既存仕様を調べ、別ファイルを担当する implementer が独立機能を実装する場合。親が子の仕事を同時に再実装しない。
同じファイル・共有設定・ロックファイル・DBスキーマの編集者は一度に1人とする。並列実装前に所有するファイルとAPI契約を決める。担当範囲が重なるなら順次実行する。
独立レビューには、実装者の結論を正解として渡さず、要件・差分・実行結果を渡す。

## 役割を選ぶ基準

振り分けるのはメイン。作業の行数やファイル数だけでは決めず、不確実性・影響範囲・検証可能性で判断する。子を呼ぶかどうかは上記の委譲条件も満たすこと。条件を満たさなければメインが直接担当する。

### 単純調査: scout / Luna low

次の全条件を満たす事実確認に使う。

- 未確認の事実が実装の判断に必要で、既存の仕様・コード・ログ・公式資料から答えられる。
- 問いと探索範囲を指定でき、設計案の優劣や複雑な原因推論を求めない。
- 読み取りだけで終わり、コード変更・リソース作成・設定変更を伴わない。

例: 「この画面を実装するファイルはどれか」「このAPIを呼ぶ場所はどこか」「失敗しているテスト名と最初のエラーは何か」「公式資料の必要権限は何か」。外部資料は案内時点の公式情報を確認する。
一度の検索ですぐ分かることはメインが直接確認する。既に証拠付きで回答済みの問いを再調査しない。「全体を調べて改善案を出す」「なぜ並行処理で壊れるか」は単純調査に含めない。

返却は原則10項目以内で、以下を含める。

1. 問いに対する結論（分からなければ未確定）。
2. 根拠のファイルと行位置、またはURL・確認日。
3. 確認した範囲と未確認部分。事実と推測を分ける。
4. 終了理由と、必要なら次の確認を一つ。

答えを特定できたら終了する。指定範囲で見つからない、情報が矛盾する、原因推論が必要になった場合もそこで親へ返し、独断で調査を拡大しない。

### 小さな限定実装: lite_worker / Luna high

次の全条件を満たす場合だけ選ぶ。

1. 仕様・入力・期待出力・受け入れ条件が確定している。
2. 参考にできる既存実装があり、新しい設計判断や技術選定が要らない。
3. 編集箇所と影響範囲を限定でき、複数機能の仕様調整が要らない。
4. 公開API契約、DBスキーマ、認証・認可、課金、秘密情報の扱い、並行処理、本番設定を変更しない。
5. 既存テストまたは小さな振る舞いテストで成否を判定でき、局所的に戻せる。

例: 既存部品の表示文言変更、指定仕様どおりの表示整形関数、既存パターンに沿った小さなUI追加とテスト。1行でも認可判定の変更なら対象外。

### 通常実装: メインまたは implementer / Sol medium

限定実装の条件を一つでも満たさない場合、または判断できない場合はこちらを選ぶ。
例: 新しい利用フローの画面・API・保存をつなぐ実装、API契約やデータ構造の変更、認証・認可処理、複数モジュールにまたがる不具合修正。
子としての implementer は分担可能な範囲だけを担当する。全体設計・契約変更の決定と統合はメインが行う。途中で限定実装の条件を外れたら、変更済み箇所と不足事項を返してSolへ引き継ぐ。

## 工程別の最小ループ

| 工程 | 基本担当と作業 | 次へ進む条件 |
| --- | --- | --- |
| 要件定義 | メイン Sol。対象ユーザー、課題、MVP、対象外、受け入れ条件を短く記録 | 主要な利用例と成功条件が検証可能 |
| 設計 | メイン Sol。画面遷移、データ、API、権限、公開先を具体化 | 重要な未決定事項とリスクが整理済み |
| 難しい設計選択 | 必要時だけ advisor。候補2〜3案と制約を比較 | 選択理由と再検討条件が記録済み |
| 土台 | メインまたは implementer。起動・テスト・ビルドの再現手順を整備 | 新しい環境で最小機能を再現できる |
| 縦切り実装 | メインまたは implementer。小さな利用シナリオ単位。定型作業だけ lite_worker | 対象テストと受け入れ条件を満たす |
| 回帰・レビュー | 決定的な検査を実行。重要差分だけ reviewer | P0/P1を修正・検証。P2/P3は記録のみで修正ループ終了 |
| ステージング | メイン。実環境に近い設定、主要導線、マイグレーションを確認 | 公開手順・復旧条件・担当が明確 |
| 本番移行 | 承認された範囲でメインが実行・監視 | デプロイ確認、主要導線、ログ・指標に問題なし |
| 運用改善 | メイン。実際の失敗や利用者の声から優先順位を更新 | 次の小さな改善が決まる |

本番移行の検証は変更のリスクに比例させる。小規模アプリに複雑なインフラや常時エージェント監視を導入することを前提としない。
レビューの優先度と修正手順は [開発フロー](development-workflow.md) の「レビュー後の修正ループ」に従う。

## Astra を使う判定

メインが次の A または B を満たすか判断し、さらに共通条件をすべて確認する。「難しそう」「ファイルが多い」「認証に関係する」だけでは呼ばない。

- **A: 重大な設計判断**。誤った判断がデータ損失・認可境界の破綻・誤課金・本番停止・大規模な作り直しにつながる。かつ、複数の具体案の比較で重要な未解決点があり、既存設計や公式仕様だけでは決定できない。例: 無停止のデータ移行順序と整合性保証の選択。
- **B: 証拠のある難解な不具合**。再現手順または十分なコード・ログの証拠があり、Sol が異なる仮説に基づく検証を2つ行っても原因を絞れない。例: 通常のテストでは出ない二重決済や競合更新。同じ操作を2回失敗しただけでは該当しない。

共通条件:

1. 問いを一つに絞り、対象コード、制約、証拠、候補または棄却済み仮説を渡せる。
2. 認証情報不足、権限不足、接続障害、ユーザーの要件選択待ちなど、モデル変更では解消しない問題ではない。
3. 通常開発の必要な判断、またはレビューで確認したP0/P1の解決に使う。P2/P3を修正するためには使わない。
4. Astraの利用可否と子の起動条件を満たす。親にもテストの整理など独立して進める有用な仕事がある。なければ無理に子を起動せず、Solで問題を限定するか、利用可能なメインのモデル切替手段で対応する。切替を行えない場合はその制約を伝える。

起動前に `判定: A/B、未解決の問い、期待する返却物` を短く示す。継続作業なら task-brief または Plan の判断欄へ残す。同一内容を複数文書へ重複記録しない。
advisor は Astra / low で、推奨、根拠、残るリスク、最小の次の検証を返す。実装と統合はSolへ戻す。Aに該当する場合は安いモデルの失敗を待たずに相談できる。
Solで複雑なロジックを追うだけならまず high を検討するが、これはAstra起動の必須前段ではない。Astraの推論量を上げる場合も、不足している判断と期待する検証を指定する。情報不足を推論量だけで埋めない。xhigh / max / ultra を通常経路に含めない。

利用率の予算は目安として、利用枠の残りが少ないと確認できた場合に、並列調査や任意レビューを減らして必須作業を優先する。残量不明なら単独作業を基本にし、使える回数を推測しない。制限を回避するためのアカウント分散や自動課金はしない。

## コンテキスト管理

最初は AGENTS.md と対象タスクを読み、対象工程の資料、必要なコードへ進む。`docs/` 全体を毎回読まない。
探索はファイル名→シンボル→該当コードと依存先の順。テスト結果は実行コマンド、終了コード、失敗テスト名、必要なスタック部分を伝える。省略したログは必要なら参照可能なローカルファイルに残し、秘密を含めない。

委譲・再開時は [task-brief](templates/task-brief.md) を使う。数値の上限より、次の作業を再現できる最小の情報を優先する。目安は30〜60行。大きな仕様は複製せずリンクで渡す。
関連タスクは同じ子の履歴を使う。別の領域へ移ったとき、矛盾した前提が残るとき、重要な制約を見落とし始めたときだけ新しい文脈へ切り替える。
圧縮は過去の料金を取り戻す機能ではない。キャッシュの割引・ヒット率も実測なしに保証しない。短さだけを理由に毎回会話を作り直さない。

長時間の処理は一度起動し、その実行IDで待つ。結果が変わらない数秒単位のポーリングや二重起動を避ける。作業待ちを別の高コストエージェントへ委譲しない。

## 小さな開発ハーネス

ここでいうハーネスは、AI が作業・検証・再開しやすい実行環境と仕組み。専用の多重オーケストレーターを作る必要はない。

- スタック決定時に、依存バージョンの固定、ロックファイル、セットアップ、起動、対象テスト、全体検査、ビルドのコマンドを README に記録する。
- 既存の Lint・型検査・テストランナーを判断の根拠にする。重要な振る舞いは失敗するテストを先に確認し、修正後に成功を確認する。文言変更だけに形だけのテストは足さない。
- チェックは対象範囲から開始し、統合時に必要な全体検査を行う。CI で同じコマンドを再現し、リリース成果物と検証対象を対応させる。
- DBを使う場合は一時DB・フィクスチャ・再現データを用意し、本番データをプロンプトへコピーしない。
- 開発・ステージング・本番の接続先を分離する。公開前にヘルスチェック、復元手順、DB変更の互換性、アプリだけ戻してよいかを確認する。
- ログやエラーにファイル位置・テスト名・相関IDなど再調査の手掛かりを持たせる。冗長ログを毎回モデルに読ませない。
- Hooks・MCP・プラグインは反復作業の必要性があるときだけ導入する。ハーネス自体の維持コストも評価する。

検証コマンドは実在するものだけを記載する。スタック未決定ならテストやデプロイコマンドを創作しない。文書・設定のみの変更は対応する構文と参照整合を確認する。

## 効果の測り方

通常の開発タスクで記録する。比較だけのために同じ有料タスクを何度も実行しない。

| 項目 | 記録内容 |
| --- | --- |
| 条件 | 日時、タスクの種類・規模、モデル、推論量、速度、子数 |
| 品質 | 受け入れ条件の達成、検証結果、後で発覚した不具合 |
| 効率 | 所要時間、手戻り回数、再調査・再起動の回数 |
| 使用量 | 取得可能なら開始・終了時の5時間枠と週枠の残率、リセット時刻 |
| 混同要因 | 他の会話の並行利用、リセットをまたいだか、キャッシュや環境の違い |

複数モデル用の枠が返る場合は枠IDごとに記録し、一つに足し合わせない。残率の差はアカウント全体の目安で、タスクの正確なトークン数ではない。リセットをまたぐ測定は差分比較から除外する。
5〜10件程度の似た仕事が自然に蓄積したら見直す。Luna の手戻りが増える仕事は Sol へ、Sol で安定する定型仕事は Luna へ。レビューや本番前確認を減らして見かけの節約率を上げない。
