Codex Core / 開発の見取り図

要件を受け取ってから
本番環境へ届けるまで

メインエージェントが全体の判断と統合を担当します。必要なときだけ子エージェントに範囲を区切って依頼し、検証結果を受け取って次へ進みます。

開発フローエージェントの関係役割とモデル推論コスト参照元

01 / End-to-end

実装から本番までの流れ

前提として、ユーザーがアプリ用フォルダを作り、Codex Core の必要な内容をコピーして、そのフォルダで Codex を開始します。ここから下が、要望を受け取った後の流れです。

1

構想を壁打ち

誰の何を解決するか、主要な利用場面、アプリ名を整理。専用 GitHub リポジトリを同じフォルダに接続。

準備と目的を確認
2

要件を定義

MVP、対象外、制約、確認可能な受け入れ条件をユーザーと決める。

docs/requirements.md
3

画面・技術を設計

画面遷移、データ、API、権限、障害時の動き、公開・復旧方針を決める。

architecture / design
4

実装計画を作る

価値とリスクを早く確かめられる小さな Step に分け、検証方法を付ける。

docs/Plan.md
5

縦切りで実装

最小の利用シナリオから画面・API・保存をつなぎ、機能を広げる。

コード＋関連テスト
6

テスト・レビュー

型・Lint・テスト・ビルド等を差分に応じて実行。重要差分は独立レビュー。

P0/P1 は修正・再検証
7

ステージング確認

本番に近い設定で主要導線を確認。環境、移行、バックアップ、復旧手順を確定。

公開前の品質ゲート
8

本番デプロイ

承認された範囲で公開。ヘルスチェック、主要導線、指標を確認し、必要ならロールバック。

公開後の監視へ
本番公開の判断点

公開対象・影響・復旧方法を示し、必要な承認を得てから実行します。課金、データ削除、外部通知も依頼と承認の範囲で扱います。

02 / Quality gates

各段階で何を確認するか

作る前

  • 目的、対象外、受け入れ条件が具体的か
  • GitHub リポジトリ、作業フォルダ、Codex プロジェクトが対応しているか
  • 認証、データ、外部サービスの重要なリスクが整理されているか

公開する前

  • 必要な静的解析・テスト・ビルドと受け入れ条件を満たしたか
  • 未解決の P0/P1 がなく、ステージングで主要導線を確認したか
  • バックアップ、復元、監視、ロールバック条件が明確か

レビュー後の追加修正は、根拠を確認した P0/P1 に限ります。P2/P3 は記録し、その修正のためのループは続けません。合意済みの受け入れ条件が未達なら完了扱いにしません。

03 / Agent orchestration

エージェントはどう連携するか

基本はメイン1人で進めます。目的と担当範囲を明確にでき、メインにも並行して有用な仕事がある場合にだけ委譲します。

メイン6.1 Sol / medium
要件・設計・判断・統合・公開
⇄
scout限定調査 → 根拠を返す
lite_worker小さな実装 → テスト結果を返す
implementer分担実装 → 変更と検証を返す
reviewer / advisor点検・相談 → 指摘や推奨を返す

親が「目的・対象ファイル・受け入れ条件・検証方法」を渡す → 子が限定作業と結果を返す → 親が確認、統合、Plan 更新、次の判断をする。標準は子0〜1人、同時最大2人。子から孫へは委譲しません。

04 / Roles

役割・モデル・推論量

次の値はこのリポジトリの設定です。実際に適用されるモデルは、使用するクライアントの選択と設定の読込状態で確認します。

役割モデル推論量担当起動の目安
メインgpt-6.1-solmedium全体の進行、設計判断、通常実装、統合、本番準備常に中心
scoutgpt-6-lunalowコード・ログ・仕様から範囲を絞った事実抽出読み取りだけで答えが出る調査
lite_workergpt-6-lunahigh仕様・テスト・既存パターンが確定した小さな実装局所的で取り消せる仕事
implementergpt-6.1-solmedium独立して分担できる通常実装と関連テストメインと編集範囲を分けられるとき
reviewergpt-6.1-solhigh重要差分の独立点検と優先度付き指摘認可・データ整合性など重要な変更
advisorgpt-6-astralow重大な設計選択や証拠のある難解な不具合の限定相談厳しい昇格条件を満たすときだけ

メイン

6.1 Sol / medium
要望を整理→設計・計画→実装・委譲→検証・統合→公開判断

要件と成果の責任者。子の報告を採用する前に確認し、Plan と品質ゲートを更新します。

scout

Luna / low
問いを受ける→範囲を検索→事実と根拠を返す

設計判断や編集はしません。答えが見つからない場合も範囲を広げず親へ返します。

lite_worker

Luna / high
確定仕様を受ける→局所実装→テスト→結果を返す

API契約、DBスキーマ、認証・認可、本番設定などを変える仕事は担当しません。

implementer

6.1 Sol / medium
担当範囲を受ける→通常実装→関連テスト→報告

機能単位の実装を分担。全体の契約や設計の採否はメインが決めます。

reviewer

6.1 Sol / high
要件・差分を受ける→独立点検→P0〜P3 を報告

重要差分だけを読み取りで確認。P0/P1 の修正後だけ、影響範囲を再点検します。

advisor

Astra / low
重大な問いを受ける→証拠・案を比較→推奨とリスクを返す

実装は行わず、相談後の実装と統合は 6.1 Sol に戻します。

05 / Usage

推論コストの考え方

low / medium / high は推論量の設定です。Plus の消費量や金額の固定倍率ではありません。モデル、推論、ツール、会話の長さ、子エージェントの作業で実際の利用量が変わります。

普段は 6.1 Sol / medium

メインが一貫して進める。小さな変更は自分で完結し、委譲の起動・統合コストを増やしません。

狭い仕事だけ委譲

単純な事実抽出は Luna / low。仕様が固まった限定実装は Luna / high。一般実装は 6.1 Sol / medium。

高い推論は必要時だけ

重要差分のレビューは 6.1 Sol / high。重大判断・難解バグだけ Astra / low に限定相談します。

評価する指標：短い回答や安いモデルの使用率ではなく、「受け入れ条件を満たした変更1件あたりの利用量・時間・手戻り」。子エージェントの作業も利用枠を消費します。API料金を Plus の残量へ換算しません。
