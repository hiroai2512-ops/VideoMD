# ゴールモードと独自プランモード

これは Codex Core の行動規則。独自プランモードは通常モード内の計画手順として運用し、Codex 内蔵の `/plan` やクライアント設定を変更しない。ゴールモードは利用可能な内蔵機能を使う。上位のツール契約・権限・モード制約を上書きしない。

## 発動条件

| 状況 | 選ぶ運用 |
| --- | --- |
| 「プランモードで」「まず計画だけ」などの明示的な依頼 | 独自プランモード。計画保存までで終了 |
| 新規アプリ、複数工程の機能で成功条件・範囲・構成が未確定 | 独自プランモードを開始し、その旨を短く伝える |
| 認証・データ移行・公開・外部サービス採用などの重要判断が未決定 | その範囲を独自プランモードで整理 |
| 要件と検証方法が明確な小修正、説明、短い調査 | 通常モード。形式的な計画書や質問を増やさない |
| 不具合調査、性能改善、移行など、結果を見て次の手を選ぶ反復作業 | 終了条件を定め、内蔵ゴールモードの候補にする |
| 上記候補に対して「ゴールモードを開始して」と明示された | 計画確定後、内蔵ゴールを作成 |

大きい作業というだけでゴールを自動作成しない。ゴールの依頼があっても終了条件が曖昧なら先に独自プランで具体化する。独自プラン中は既存ゴールの実装継続を利用しない。実装ゴールが既に活動中なら、計画に専念するための一時停止をユーザーに依頼し、明示的な停止指示を受けて内蔵機能で停止する。

## 独自プランモードの手順

### 1. 現状を調べる

Git状態、対象に近い指示、関連仕様・コード・テストを必要な範囲だけ読む。調べれば分かる事実をユーザーへの質問にしない。既存変更を保持し、実現可能性と重要な未決事項を絞る。読み取りや追跡対象を変えない検証は実行できる。

この段階ではアプリコード・依存関係・DB・外部リソースを変更しない。内蔵プランと共通する「先に調査し、対話で判断を揃え、実装せず計画を渡す」挙動を再現する。ただし、通常モードで計画文書を保存することは、この独自運用で認める。実際の内蔵プランが上位指示で有効な場合はその制約を優先し、保存できなければ本文を提示して未保存と伝える。

### 2. ステップバック・クエスチョンで目的を明確にする

個別の機能や技術から一歩戻り、解決したい課題を質問する。一度に1〜3問を目安とし、回答済みの質問は繰り返さない。構想整理では少なくとも目的に戻る問いを使い、ユーザーが既に答えを示していればその回答を要約して使う。

- 誰が、どの場面で、何に困っていますか。今はどう対処していますか。
- その機能が実現すると、何ができれば成功と言えますか。
- 最初の版で一つだけ解決するなら何ですか。後回しにできるものは何ですか。
- 外部サービスなし・無料で始める場合、どの制約なら受け入れられますか。

回答を「課題→利用シナリオ→最小機能→確認可能な受け入れ条件→実装Step」に変換する。例えば「入力し直す手間を減らす」は「保存した内容を再起動後も表示できる」という条件にし、保存・再表示・検証を一つの縦切りStepにする。解決策を先に決めつけない。

安全、課金、公開範囲、必須機能を変える未決事項は回答を待つ。通常の実装判断は既存パターンと簡潔な推奨案で決め、仮定を記録する。任意の見た目の好みまで質問して計画を長引かせない。

### 3. 計画を確定し保存する

目的・対象ユーザー・成功条件・対象内外・制約・現状・主要な判断が揃ったら終了する。各実装タスクの対象、依存、入出力や必要な契約、検証方法を具体化し、実装担当が重要判断をやり直さず着手できる粒度にする。細かな命名や装飾まで決める必要はない。

成果物は [文書管理](documentation.md) に従って保存する。

- 要件と受け入れ条件: `docs/requirements.md`。
- 構成と選定理由・外部サービスの比較: `docs/architecture.md` と必要な `docs/design/`。
- 実装計画書: `docs/Plan.md`。StepごとのID付きチェックボックス、依存条件、完了条件、要件ID、検証方法を含む。計画時の実装項目はすべて `[ ]`。

小変更では必要なPlan項目だけに絞る。最終出力は目的・主要判断・料金比較（該当時）・保存した文書・最初のStep・判断待ちを短く示す。計画だけを依頼された場合はここで終了する。最初から実装まで依頼され、重要判断が解消していれば、保存後に実装へ進める。計画終了の定型的な再承認は求めない。課金や本番操作の承認は別途その範囲に従う。

## 内蔵ゴールモードの実行

開始前に、目的、完了の証拠、維持する制約、許可された作業範囲、反復の判断方法、停止・ブロック条件を短く定める。トークン予算はユーザーが指定したときだけ設定し、時間・使用量の制約を勝手に数値へ換算しない。

1. 内蔵ゴールの状態を確認する。未完了の別ゴールを上書きしない。
2. 明示的な開始依頼と、利用可能な作成ツールがある場合に内蔵ゴールを作る。ツールがなければ利用不可と伝え、通常の依頼範囲で続行する。文書のチェックリストを内蔵ゴールが起動した証拠にしない。
3. 作業→対象の検証→完了条件との比較→次の有用な作業を繰り返す。進捗はPlanに必要な節目で記録する。
4. 完了の証拠が揃った場合だけ完了状態へ更新する。予算切れや未実行の検証を完了にしない。
5. 一時停止は明示的な依頼に従う。再開・解除・予算制御はユーザーまたはシステムの操作に従い、利用可能なツール契約を優先する。ブロックは同じ障害が3ターン連続し、ユーザー入力や外部変化なしでは有用な進捗を出せない場合に記録する。再開後は連続回数を数え直す。

モードの使用は、プッシュ、課金、本番操作、外部通知の新たな許可を意味しない。終了・中断時には証拠、残作業、ローカル保存・コミット・プッシュの実際の状態を報告する。

## 速度と完成度

全モードで完成度6割程度のMVPを標準にする。主要な利用導線、必須の受け入れ条件、変更に必要な検証を満たしたら、装飾、網羅的な便利機能、将来向けの抽象化、過剰な文書化は後回しにする。後回しの項目を対象外として明記し、未達の必須条件を完了扱いにしない。必要なアクセシビリティも維持する。

セキュリティ、プライバシー、データ保全と、外部サービスの料金・規約・権限・秘密値・障害対応には6割基準を適用しない。料金比較は [開発フロー](development-workflow.md#外部サービスの料金と無料案) に従う。速度優先を理由にFast課金や追加クレジット購入を自動で行わない。

## 根拠と適用範囲

独自プランの発動条件、質問方法、計画文書の保存例外、6割MVP基準はユーザー要望を採用したリポジトリ独自の運用。内蔵モードの権限制御や自動継続を実装したものではない。参考共有リンクはブラウザでも「この ChatGPT の会話を読み込めませんでした」となり、本文を確認できなかったため、依頼本文の5点を採用根拠とした。
